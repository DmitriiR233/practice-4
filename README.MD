# Учет финансов

## Общая идея решения

В данном проекте реализована доменная модель для модуля "Учет финансов" с использованием различных паттернов проектирования и принципов SOLID и GRASP. Основной функционал включает создание, редактирование и удаление счетов, категорий и операций. Также реализована аналитика, импорт и экспорт данных, управление данными и статистика.

## Принципы SOLID и GRASP

### SOLID
- **Single Responsibility Principle (SRP)**: Каждый класс имеет одну ответственность. Например, `BankAccountService` отвечает только за операции с счетами.
- **Open/Closed Principle (OCP)**: Классы открыты для расширения, но закрыты для модификации. Например, `DataImporter` можно расширить для поддержки новых форматов данных.
- **Liskov Substitution Principle (LSP)**: Подклассы могут заменять свои базовые классы без изменения корректности программы. Например, `CSVDataImporter` можно заменить на `JSONDataImporter`.
- **Interface Segregation Principle (ISP)**: Клиенты не должны зависеть от интерфейсов, которые они не используют. Например, `IDataExporter` имеет отдельные методы для каждого типа данных.
- **Dependency Inversion Principle (DIP)**: Модули высокого уровня не должны зависеть от модулей низкого уровня. Оба должны зависеть от абстракций. Например, `BankAccountService` зависит от `IBankAccountProvider`, а не от конкретной реализации.

### GRASP
- **High Cohesion**: Классы имеют высокую кохезсию, так как каждая функция выполняет одну задачу. Например, `BankAccountService` содержит только методы для работы с счетами.
- **Low Coupling**: Классы имеют низкую связанность, так как зависимости между ними минимальны. Например, `BankAccountService` зависит только от `IBankAccountProvider`.

## Паттерны GoF

### Порождающие паттерны
- **Фабрика**: `BankAccountFactory`, `CategoryFactory`, `OperationFactory`, `DataExporterFactory`, `DataImporterFactory` гарантируют, что все доменные объекты создаются в одном и том же месте кода.
- **Команда**: `Command` и его реализации (`CreateBankAccountCommand`) позволяют представить пользовательские сценарии в виде объектов.
- **Декоратор**: `CommandDecorator` и его реализации (`TimingCommandDecorator`) позволяют добавлять дополнительное поведение к командам.

### Структурные паттерны
- **Фасад**: `BankAccountFacade`, `CategoryFacade`, `OperationFacade` объединяют по смыслу несколько методов.
- **Посетитель**: `DataExporterVisitor` и его реализации (`CSVDataExporterVisitor`) позволяют выполнять операции над объектами без изменения их классов.

### Поведенческие паттерны
- **Шаблонный метод**: `DataImporter` и его реализации (`CSVDataImporter`) позволяют определить скелет алгоритма, оставляя реализацию шагов подклассам.
